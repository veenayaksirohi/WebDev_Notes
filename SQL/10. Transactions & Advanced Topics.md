## 📝 Overview

Transactions group multiple SQL statements into a single unit of work. A transaction either **succeeds completely** (committed) or **fails completely** (rolled back). Understanding transactions, isolation levels, locks, stored routines, and triggers is essential for building reliable, concurrent database applications.

---

## 🧩 ACID Properties

- **Atomicity** — All statements in a transaction succeed or none do.
    
- **Consistency** — Database moves from one valid state to another (integrity constraints preserved).
    
- **Isolation** — Concurrent transactions behave as if executed serially (to some degree determined by isolation level).
    
- **Durability** — Once committed, changes survive crashes and power loss.
    

**Interview tip:** Explain with a money-transfer example — debit and credit must both happen or neither.

## 🛠️ Transaction Control (BEGIN / COMMIT / ROLLBACK)

```sql
-- start a transaction
BEGIN; -- or START TRANSACTION; (DB-specific)

-- statements
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- commit or rollback
COMMIT; -- persists changes
-- ROLLBACK; -- undoes changes since BEGIN
```

**Savepoints** (partial rollback inside a transaction):

```sql
SAVEPOINT sp1;
-- do some work
ROLLBACK TO sp1; -- undo to savepoint
```

## 🔒 Locks & Isolation Levels

Concurrency control uses locks and multiversioning. Behavior varies by DB (e.g., PostgreSQL uses MVCC; MySQL InnoDB blends locks + MVCC).

### Transaction isolation levels explained

From weakest → strongest:

1. **READ UNCOMMITTED** — allows dirty reads (rarely used)
    
2. **READ COMMITTED** — sees only committed data (prevents dirty reads)
    
3. **REPEATABLE READ** — ensures repeated reads within a txn see the same rows (prevents non-repeatable reads)
    
4. **SERIALIZABLE** — strongest; transactions behave as if run one after another (prevents phantoms)
    

DB-specific notes:

- MySQL InnoDB default historically `REPEATABLE READ` (with gap-locks to avoid phantoms).
    
- PostgreSQL default is `READ COMMITTED`.
    

### Anomalies / phenomena

- **Dirty read** — reading uncommitted data from another txn.
    
- **Non-repeatable read** — row changes between two reads in same txn.
    
- **Phantom read** — new rows appear in a range between two reads.
    

Map anomalies to isolation levels when answering interview questions.

### Lock types & behavior (brief)

- **Shared (S) / Read locks** — multiple txns can read.
    
- **Exclusive (X) / Write locks** — only one txn can write.
    
- **Row-level vs table-level locks** — row locks more granular; table locks coarser.
    
- **Intent locks** (SQL Server) indicate intention to acquire row locks.
    

Use `SELECT ... FOR UPDATE` to explicitly acquire row-level X locks for updates:

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

## 🧰 Stored Procedures & Functions

Stored routines encapsulate logic inside the DB server — useful for performance, reusability, and enforcing business logic close to data. Be aware of portability and maintainability trade-offs.

### MySQL example (procedure & function)

```sql
DELIMITER $$
CREATE PROCEDURE transfer_funds(IN from_id INT, IN to_id INT, IN amt DECIMAL)
BEGIN
  START TRANSACTION;
  UPDATE accounts SET balance = balance - amt WHERE id = from_id;
  UPDATE accounts SET balance = balance + amt WHERE id = to_id;
  COMMIT;
END$$
DELIMITER ;

-- function example
CREATE FUNCTION get_balance(acc_id INT) RETURNS DECIMAL(10,2)
DETERMINISTIC
RETURN (SELECT balance FROM accounts WHERE id = acc_id);
```

### PostgreSQL example (function)

```sql
CREATE OR REPLACE FUNCTION transfer_funds(from_id INT, to_id INT, amt NUMERIC)
RETURNS VOID LANGUAGE plpgsql AS $$
BEGIN
  UPDATE accounts SET balance = balance - amt WHERE id = from_id;
  UPDATE accounts SET balance = balance + amt WHERE id = to_id;
END; $$;
```

**Notes:**

- Functions often return a value; procedures (in some DBs) do not.
    
- Transaction control inside functions/procedures may be restricted in some DBs (e.g., PostgreSQL functions cannot commit/rollback mid-function).

## ⚡ Triggers (automatic DB actions)

Triggers run automatically on table events: `BEFORE/AFTER INSERT`, `UPDATE`, `DELETE`. Use them for auditing, denormalization, validations, or cascading side-effects.

### Row-level vs Statement-level

- **Row-level triggers**: run once per affected row
    
- **Statement-level triggers**: run once per statement regardless of affected row count
    

### Trigger examples

**Audit insert (Postgres syntax example)**

```sql
CREATE TABLE audit_log (
  id SERIAL PRIMARY KEY,
  table_name TEXT,
  operation TEXT,
  changed_by TEXT,
  changed_at TIMESTAMP DEFAULT now()
);

CREATE OR REPLACE FUNCTION log_employee_insert() RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO audit_log(table_name, operation, changed_by)
  VALUES ('employees', 'INSERT', current_user);
  RETURN NEW;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_emp_insert
AFTER INSERT ON employees
FOR EACH ROW EXECUTE FUNCTION log_employee_insert();
```

**Before update validation (MySQL example)**

```sql
CREATE TRIGGER before_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
  IF NEW.salary < 0 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Salary cannot be negative';
  END IF;
END;
```

**Caution:** Triggers can hide logic and cause unexpected side effects; document them well.

## ✅ Best Practices

- Keep transactions **short** — hold locks for the minimal time
    
- Use appropriate **isolation level** for your workload (balance correctness vs concurrency)
    
- Prefer application-level validation for complex business logic; use stored routines/triggers for critical, low-latency work
    
- Monitor slow queries and high lock contention (`pg_stat_activity`, `INFORMATION_SCHEMA`, `SHOW ENGINE INNODB STATUS`)
    
- Test stored procedures/triggers carefully and document behavior
    

---

## ⚠️ Common Pitfalls

- Long-running transactions causing lock contention and bloat
    
- Relying on serializable isolation without understanding performance cost
    
- Using triggers to do heavy computation or external I/O (can block transactions)
    
- Expecting portable behavior across DB engines (transaction features differ)

## 🔍 Interview Questions (quick)

|#|Question|Key Points to Cover|
|---|---|---|
|1|What are ACID properties?|Atomicity, Consistency, Isolation, Durability|
|2|How does SERIALIZABLE differ from READ COMMITTED?|Stronger guarantees; prevents phantoms; may use predicate locks or serialization checks|
|3|When would you use SAVEPOINT?|Partial rollback inside large transactions|
|4|Can you commit inside a PostgreSQL function?|No — functions run in the caller’s transaction; use procedures (Postgres 11+) or external control|
|5|What is a deadlock and how do you resolve it?|Two txns waiting on resources; resolved by DB killing one txn; avoid by consistent lock ordering and short txns|
