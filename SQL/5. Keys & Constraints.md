## 📝 Overview

Keys and constraints are mechanisms to **ensure data integrity** and **uniqueness** in relational databases. They help model real-world relationships and enforce business rules at the database level.

Common constraints covered here:

- `PRIMARY KEY`
    
- `FOREIGN KEY`
    
- `UNIQUE`
    
- `NOT NULL`, `CHECK`, `DEFAULT` (referenced in DDL)
    
- Composite and theoretical keys (candidate / super / alternate)
    

---

## 🔑 Primary Key

- A **Primary Key (PK)** uniquely identifies each row in a table.
    
- By definition: **UNIQUE + NOT NULL**.
    
- A table typically has **one** primary key (single column or composite).
    

### Syntax

```sql
CREATE TABLE departments (
  dept_id INT PRIMARY KEY,
  name VARCHAR(100) NOT NULL
);
```

### Composite Primary Key

```sql
CREATE TABLE course_enrollments (
  student_id INT,
  course_id INT,
  enrollment_date DATE,
  PRIMARY KEY (student_id, course_id)
);
```

---

## 🌉 Foreign Key

- A **Foreign Key (FK)** enforces referential integrity between two tables.
    
- It ensures values in the child table correspond to existing values in the parent table.
    
- Supports actions: `ON DELETE` / `ON UPDATE` (`CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`)
    

### Syntax

```sql
CREATE TABLE employees (
  id INT PRIMARY KEY,
  name VARCHAR(100),
  dept_id INT,
  FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);
```

### With cascade

```sql
FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
  ON DELETE SET NULL
  ON UPDATE CASCADE
```

---

## 🧾 Unique Key

- Ensures **no duplicate** values in the specified column(s).
    
- Unlike `PRIMARY KEY`, a table can have **multiple UNIQUE constraints**.
    
- **NULL behavior varies by DBMS** — some allow multiple NULLs, others restrict them.
    

### Syntax

```sql
CREATE TABLE users (
  id INT PRIMARY KEY,
  email VARCHAR(150) UNIQUE
);
```

---

## 🧠 Candidate / Super / Alternate Keys

- **Super Key**: Any set of columns that uniquely identifies a row (may contain extra columns).
    
- **Candidate Key**: A minimal super key — no subset of columns can uniquely identify the row.
    
- **Primary Key**: A candidate key chosen as the main identifier.
    
- **Alternate Key**: Candidate keys that were not chosen as the primary key.
    

**Example:** If `employees` has columns `(emp_id, email, ssn)` and each is unique:

- Super keys: `(emp_id)`, `(email)`, `(ssn)`, `(emp_id, email)`, etc.
    
- Candidate keys: `(emp_id)`, `(email)`, `(ssn)`
    
- If `emp_id` chosen as PK, `email` and `ssn` are alternate keys.
    

---

## 🔗 Composite Keys

- A composite key uses **multiple columns** together to form uniqueness.
    
- Useful when no single column uniquely identifies a row.
    

### Example (already shown above)

`PRIMARY KEY (student_id, course_id)`

**Note:** Composite keys are common in join tables and many-to-many relationships.

## 🛠️ Adding Constraints (ALTER TABLE)

### Add Primary Key

```sql
ALTER TABLE employees
ADD PRIMARY KEY (id);
```

### Add Foreign Key

```sql
ALTER TABLE employees
ADD CONSTRAINT fk_dept
FOREIGN KEY (dept_id) REFERENCES departments(dept_id);
```

### Add Unique Constraint

```sql
ALTER TABLE users
ADD CONSTRAINT uq_email UNIQUE (email);
```

## ✅ Best Practices

- Choose **stable, surrogate or natural** keys thoughtfully (surrogate: `id` INT; natural: `email` if immutable)
    
- Use **surrogate keys** for simplicity and indexing in large systems
    
- Index foreign keys for performance on joins
    
- Keep composite keys minimal
    
- Use constraints to enforce business rules at DB level
    

---

## ⚠️ Common Pitfalls

- Relying on mutable natural keys (e.g., email) as PK
    
- Forgetting to index foreign key columns (slow joins)
    
- Misunderstanding NULL behavior with UNIQUE across DBs
    
- Overusing composite keys when a surrogate key would be cleaner

## 🔍 Interview Questions

|#|Question|Key Points to Cover|
|---|---|---|
|1|What is a primary key?|Unique + NOT NULL, single or composite|
|2|Difference between PRIMARY KEY and UNIQUE?|PK implies NOT NULL; UNIQUE allows NULLs (DB-specific)|
|3|What is referential integrity?|Foreign keys maintaining relationships|
|4|When to use composite keys?|Many-to-many / join tables|
|5|What are candidate keys?|Minimal unique column sets|

### Interview Tip

👉 When asked, discuss trade-offs: surrogate vs natural keys, indexing costs, and how constraints affect application design.
