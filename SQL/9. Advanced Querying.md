## 📝 Overview

Advanced querying features let you express complex logic clearly and make queries efficient. This note covers **CTEs (including recursive)** for readability and recursion, **pivot/unpivot** for reshaping data, **indexes** for speed, and **views** for abstraction and security.

Examples use simple `employees`, `sales`, and `departments` tables so you can paste and run them in any SQL environment.

---

## 🔁 Common Table Expressions (CTE)

A CTE is a named temporary result set usable within a single statement. It improves readability and modularises complex queries.

### Non-recursive CTEs

Example: top earners per department

```sql
WITH dept_avg AS (
  SELECT dept_id, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY dept_id
)
SELECT e.id, e.name, e.salary, d.avg_salary
FROM employees e
JOIN dept_avg d ON e.dept_id = d.dept_id
WHERE e.salary > d.avg_salary;
```

**Why use CTEs?**

- Break complex queries into named parts
- Avoid repeating subqueries
- Improve readability for interview explanations

### Multiple CTEs & chaining

You can define multiple CTEs separated by commas and reference them sequentially.

```sql
WITH recent_sales AS (
  SELECT * FROM sales WHERE order_date >= '2025-01-01'
),
customer_totals AS (
  SELECT customer, SUM(amount) AS total
  FROM recent_sales
  GROUP BY customer
)
SELECT * FROM customer_totals WHERE total > 1000;
```

### Recursive CTEs (hierarchical data)

Recursive CTEs are used for hierarchical queries like org charts, bill-of-materials, or folder trees.

**Tables (employees)**

| id  | name  | manager_id |
| --- | ----- | ---------- |
| 1   | Amit  | NULL       |
| 2   | Neha  | 1          |
| 3   | Rahul | 2          |
| 4   | Sana  | 2          |

**Recursive CTE — get hierarchy under Amit**

```sql
WITH RECURSIVE team AS (
  -- anchor member
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE id = 1
  UNION ALL
  -- recursive member: find direct reports
  SELECT e.id, e.name, e.manager_id, t.depth + 1
  FROM employees e
  JOIN team t ON e.manager_id = t.id
)
SELECT * FROM team ORDER BY depth;
```

**Notes:**

- Anchor member + recursive member
- Many DBs limit recursion depth by default (e.g., PostgreSQL) — be mindful
- Useful for tree traversals, path generation, aggregation over hierarchies

## 🔄 Pivoting & Unpivoting (row ⇄ column)

Pivoting transforms row values into columns; unpivoting does the reverse. Support varies by DB: SQL Server has `PIVOT`/`UNPIVOT`, PostgreSQL uses `crosstab()`, MySQL uses `CASE` expressions.

### Pivot example (sales by quarter per product) — portable using CASE

**sales table**

| product | quarter | amount |
| ------- | ------- | ------ |
| A       | Q1      | 100    |
| A       | Q2      | 150    |
| B       | Q1      | 200    |

**Query (portable)**

```sql
SELECT product,
  SUM(CASE WHEN quarter = 'Q1' THEN amount ELSE 0 END) AS q1,
  SUM(CASE WHEN quarter = 'Q2' THEN amount ELSE 0 END) AS q2,
  SUM(CASE WHEN quarter = 'Q3' THEN amount ELSE 0 END) AS q3,
  SUM(CASE WHEN quarter = 'Q4' THEN amount ELSE 0 END) AS q4
FROM sales
GROUP BY product;
```

### Unpivot example (convert columns back to rows)

```sql
-- Suppose we have product, q1, q2, q3, q4
SELECT product, 'Q1' AS quarter, q1 AS amount FROM product_quarter
UNION ALL
SELECT product, 'Q2', q2 FROM product_quarter
-- and so on
```

**DB-specific features**

- SQL Server: `PIVOT` / `UNPIVOT`
- PostgreSQL: `crosstab()` extension
- MySQL: use `CASE` or JSON functions

## ⚡ Indexes (performance optimisation)

Indexes are data structures that speed up lookups and ordered scans at the cost of storage and slower writes.

### Types of indexes

- **B-tree (default)**: Good for range scans, equality, ordering
- **Hash**: Fast equality lookups (Postgres supports hash indexes but B-tree preferred)
- **Bitmap**: For low-cardinality columns (specialized)
- **GIN / GiST**: For full-text, arrays, JSON, geometric types
- **Clustered index**: Physically orders table rows (SQL Server / MySQL InnoDB primary key)

### When to add an index

- Columns used frequently in `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY`
- Columns used in selective predicates (high cardinality)

**Don't index**

- Very low-cardinality columns (e.g., boolean flags) unless used in filtered indexes
- Columns updated frequently if index maintenance cost outweighs benefits

### Creating / dropping indexes

```sql
-- create a single-column index
CREATE INDEX idx_emp_dept ON employees(dept_id);

-- composite index (prefix matters)
CREATE INDEX idx_emp_dept_salary ON employees(dept_id, salary);

-- drop
DROP INDEX idx_emp_dept; -- syntax varies by DB (e.g., MySQL: DROP INDEX idx ON table)
```

### Using EXPLAIN / ANALYZE

- Always examine the query plan (`EXPLAIN`, `EXPLAIN ANALYZE`) to verify index usage
- Look for index scans, sequential scans, and estimated vs actual rows

### Index pitfalls & maintenance

- **Write amplification**: indexes slow `INSERT`/`UPDATE`/`DELETE`
- **Stale statistics**: run `ANALYZE` / `VACUUM` (Postgres) or `OPTIMIZE` (MySQL) when needed
- **Too many indexes**: more storage & slower writes
- **Missing index on join column**: slow join performance

## 🧾 Views & Materialized Views

Views are saved queries (virtual tables). Materialized views store results physically for faster reads.

### CREATE VIEW examples

```sql
CREATE VIEW active_employees AS
SELECT id, name, dept_id
FROM employees
WHERE active = TRUE;

-- use it like a table
SELECT * FROM active_employees WHERE dept_id = 10;
```

**Advantages of views**

- Simplify complex queries
- Encapsulate business rules
- Provide abstraction and security (restrict columns)

**Limitations**

- Some views are not updatable
- Complex views may be slow because they run underlying queries each time

### Materialized views

- Store the result set physically and need to be refreshed
- Useful for expensive aggregations and reporting

```sql
-- PostgreSQL example
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT date_trunc('month', order_date) AS month,
       SUM(amount) AS total
FROM sales
GROUP BY month;

-- refresh
REFRESH MATERIALIZED VIEW monthly_sales;
```

### Security & privileges

- Grant `SELECT` on views instead of underlying tables to limit access
- Be careful with definer/invoker rights (some DBs allow view to run with definer privileges)

## ✅ Best Practices

- Use CTEs to break down complex logic — but avoid excessive nesting that harms performance
- Test recursive CTEs for termination and depth issues
- Use `EXPLAIN` to justify index creation
- Prefer covering indexes (indexes including all queried columns) for critical queries
- Use views for abstraction and security, materialized views for heavy aggregations

---

## ⚠️ Common Pitfalls

- Expecting CTEs to be automatically inlined — some DBs treat them as optimization barriers
- Creating indexes without understanding query patterns (unused indexes waste resources)
- Overusing materialized views without refresh strategy
- Assuming pivot syntax is portable across DBs
