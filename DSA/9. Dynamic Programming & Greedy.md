## 📝 Overview

Dynamic Programming (DP) and Greedy are two core algorithmic paradigms frequently tested in interviews. DP is used when problems exhibit **overlapping subproblems** and **optimal substructure** and often requires careful state design. Greedy makes locally optimal choices hoping to reach a global optimum — fast and simple when it applies.

This note explains both paradigms, shows classic problems, gives code sketches, and lists interview-style questions and tips.

---

## 🔁 DP Fundamentals

### Overlapping subproblems

A problem has overlapping subproblems when the same subproblems are solved multiple times during naive recursion (e.g., naive Fibonacci recalculates `fib(k)` many times). Memoization or tabulation avoids duplicate work.

### Optimal substructure

A problem has optimal substructure if an optimal solution can be composed from optimal solutions of its subproblems. For example, shortest path and many DP problems satisfy this.

**Rule of thumb:** If both properties hold, DP is a good candidate.

## 🛠️ DP Techniques & State Design

### Memoization (top-down)

* Write recursive solution; cache results in a hash map / array.
* Easy to implement; good for sparse states.

**Sketch (Fibonacci):**

```python
memo = {}
def fib(n):
    if n < 2: return n
    if n in memo: return memo[n]
    memo[n] = fib(n-1) + fib(n-2)
    return memo[n]
```

### Tabulation (bottom-up)

* Fill DP table iteratively from base cases to target.
* Often more space/time predictable and avoids recursion limits.

**Sketch (Fibonacci):**

```python
dp = [0]*(n+1)
dp[0], dp[1] = 0, 1
for i in range(2, n+1): dp[i] = dp[i-1] + dp[i-2]
return dp[n]
```

### State & transition design tips

* Identify parameters that uniquely define a subproblem (index, remaining capacity, last-picked index, mask for bitmask DP).
* Decide whether state needs extra info (e.g., previous element, remaining budget).
* Try to write recurrence before coding; small examples help validate.
* For optimization: consider reducing state dimension (rolling arrays) or converting to greedy if possible.

## 📚 Classic DP Problems (with sketches)

### 0/1 Knapsack (DP)

**Problem:** Given `n` items (weight, value), capacity `W`, maximize value selecting items at most once.

**DP state:** `dp[i][w]` = max value using first `i` items with capacity `w`.

**Recurrence:**

```
dp[i][w] = max(dp[i-1][w], dp[i-1][w-weight_i] + value_i)  # if w >= weight_i
```

**Complexity:** `O(n*W)` time, `O(n*W)` space (can be optimized to `O(W)` rolling array).

---

### Longest Increasing Subsequence (LIS)

* **DP O(n^2):** `dp[i] = 1 + max(dp[j]) for all j < i and a[j] < a[i]` → O(n^2)
* **Patience/Greedy + binary search O(n log n):** maintain tails array where `tails[len]` = smallest tail of an increasing subsequence of length `len`.

**Patience sketch:**

```python
import bisect
tails = []
for x in arr:
  i = bisect_left(tails, x)
  if i == len(tails): tails.append(x)
  else: tails[i] = x
return len(tails)
```

---

### Longest Common Subsequence (LCS)

**DP state:** `dp[i][j]` = LCS length of `A[:i]` and `B[:j]`.

```
if A[i-1]==B[j-1]: dp[i][j] = dp[i-1][j-1] + 1
else: dp[i][j] = max(dp[i-1][j], dp[i][j-1])
```

**Complexity:** `O(n*m)` time & space (can optimize space to `O(min(n,m))`).

---

### Coin Change (min coins & ways)

* **Min coins:** `dp[x] = 1 + min(dp[x - coin])` for coins if reachable; base `dp[0] = 0`.
* **Ways to make amount:** `dp[x] += dp[x - coin]` iterating coins outer loop to avoid reorder duplicates.

**Complexities:** `O(amount * num_coins)`.

---

### House Robber / Staircase / Partition DP patterns

* House Robber (no adjacent picks) → `dp[i] = max(dp[i-1], dp[i-2] + val[i])` (1D DP)
* Staircase (climbing steps) → Fibonacci-like `dp[i] = dp[i-1] + dp[i-2]` or generalized to `k` steps
* Partition/Subset-sum → bitset optimization: use bitset shifts for performant subset checks

## 🏁 Greedy Algorithms

### Greedy paradigm explained (when it works)

Greedy chooses locally optimal choices hoping they lead to global optimum. Greedy is correct when **a matroid structure or greedy-choice property** and **optimal substructure** hold. Prove correctness by exchange argument or induction.

**Signs greedy might work:**

* Problem asks for min number of intervals/points, scheduling, or Huffman-like compression
* You can show a locally optimal choice can be swapped into any optimal solution without worsening it

---

### Classic greedy problems & sketches

#### Activity selection / interval scheduling

**Goal:** select max number of non-overlapping intervals.
**Greedy:** sort by finish time, pick intervals with earliest finish compatible with chosen set.
**Complexity:** `O(n log n)` for sort + `O(n)` scan.

#### Interval covering / minimum intervals to cover a range

**Greedy:** sort by start, always pick interval with farthest end that starts before current uncovered point.

#### Huffman coding (optimal prefix codes)

Build min-heap of symbol frequencies; repeatedly pop two smallest, combine them into node with summed frequency, push back. Tree yields optimal prefix codes.

#### Greedy in MST (Kruskal/Prim)

Both Kruskal and Prim are greedy algorithms: pick smallest edge that doesn't break forest connectivity (Kruskal) or smallest crossing edge (Prim).

---

## ⚖️ DP vs Greedy: How to choose

* Try greedy first if natural local choice exists; attempt exchange argument.
* If greedy fails on a counterexample, search for DP state: can we define overlapping subproblems?
* DP is general but slower; greedy is faster but requires proof.

---

## ✅ Best Practices & Patterns

* Draw small examples and check greedy choices — if a counterexample exists, DP may be necessary.
* For DP, clearly define state and transitions before coding; test on base cases.
* Use memoization for sparse state spaces; use tabulation and rolling arrays for tight memory.
* Optimize using binary search (LIS) or bitsets (subset sums) where applicable.

---

## ⚠️ Common Pitfalls

* Writing DP with wrong state (missing parameter leading to incorrect recomputation)
* Off-by-one in indices for DP tables
* Assuming greedy works without proof — present a short exchange argument in interviews
* Not handling large constraints (need to switch to optimized approaches)
